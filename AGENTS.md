# AGENTS.md — Чувствительность таксономического профиля бактериальных сообществ городских почв Москвы к выбору классификатора и референсной базы данных

## 0. Цель и образ результата

Методологический вопрос проекта: насколько таксономический состав бактериальных сообществ почв Москвы (16S рРНК, V4–V5, QIIME 2 2025.7) и выводы о нём зависят от классификатора и референсной базы при фиксированной обработке ридов.

**Текущий этап: всё до сравнения классификаторов** — подсчёт ридов, импорт и сводка качества, денойзинг, классификация. Сравнение методов (таблица соответствий номенклатур, доля неклассифицированных, согласованность, отчёт) на этом этапе не делается и не начинается.

Методы этапа — три запуска `classify-sklearn` с готовыми классификаторами и пороги по умолчанию (`confidence 0.7`): `sklearn_silva138`, `sklearn_gtdb`, `sklearn_gg2`. Методы `classify-consensus-vsearch` и `classify-consensus-blast` отложены: им нужны референсные FASTA и таксономия SILVA, которых в `data/refs/` нет.

В конце этапа в проекте существуют:
- `results/read_counts_R1.tsv` — число и длина ридов по 11 образцам: `sample-id`, `reads_R1`, `reads_R2`, `mean_len_R1`, `min_len_R1`, `max_len_R1`;
- `work/qza/raw_reads_single.qza` и `work/qzv/reads_summary.qzv` — импорт и сводка качества;
- `memory/denoise_choice.md` — решение человека, строки `trim-left: <число>` и `trunc-len: <число>` и обоснование;
- `work/qza/ASV_table.qza`, `work/qza/rep_seq.qza`, `work/qza/dada2_stats.qza`, `work/qzv/dada2_stats.qzv` — результат денойзинга;
- `work/qza/taxonomy_sklearn_silva138.qza`, `work/qza/taxonomy_sklearn_gtdb.qza`, `work/qza/taxonomy_sklearn_gg2.qza` — таксономия трёх методов;
- `data/refs/VERSIONS.md` — источник, дата и sha256 каждого из трёх классификаторов;
- `diary.md` — журнал.

Ничего больше создавать не надо, кроме артефактов графа проекта (ниже) и экспорта сводки качества в `work/qzv_export/`.

### Граф проекта

Параллельно с работой проект ведётся как хранилище Obsidian: каждый файл проекта — узел графа, ссылки `[[…]]` — рёбра. Человек ставит задачи словами в сессии. Твоя работа:

1. записать задачу человека заметкой в `tasks/` и разделить её на подзадачи, если необходимо;
2. выполнять подзадачи по очереди, вести их статусы и по каждой сообщать итог;
3. по ходу работы достраивать граф по онтологии `ontology.yaml`.

Новая сессия начинается с чтения `STATUS.md` и `tasks/`: по статусам определи, что сделано, что в работе и что ждёт человека.

Малая цель графа — подсчёт ридов и оценка их качества по 11 образцам. Первая задача — «Подсчитать риды и оценить их качество», вторая, опирающаяся на первую, — «Составить отчёт о числе и качестве ридов» (формулировки и условия — в 2.4). Граф должен отвечать на компетентностные вопросы из `ontology.yaml`: какие образцы и какого рода входят в набор; в каком файле лежат риды образца и где записано их число; каким экспериментом, методом и проверкой получен результат; какие задачи выполнены и чем закрыты; на каких результатах основан отчёт.

После каждого сообщения человека в проекте существуют:
- заметки задач и подзадач в `tasks/` с актуальными статусами и итогами;
- результаты выполненных подзадач — то, что требует их «Готово, когда»;
- заметки обо всех объектах работы в `notes/`, связанные между собой и с файлами;
- заметки классов онтологии в `ontology/`; настройки хранилища в `.obsidian/`.

## 1. Критерий готовности

Этап считается выполненным, когда проходит проверка (из корня проекта, в окружении `qiime2-amplicon-2025.7`):

```
conda run --no-capture-output -n qiime2-amplicon-2025.7 python3 checks/check.py
```

Проверка возвращает 0 при успехе и 1 при любом провале, провалы печатает списком. Она проверяет:
- метаданные и манифест: 11 образцов (`K_S63` — `negative_control`, остальные `soil`), в манифесте только R1, все файлы существуют; контрольные суммы `data/raw/` совпадают с `data/raw.sha256`; `data/raw/` и `checks/` закрыты от записи;
- число ридов: `reads_R1 == reads_R2`, и то же число у каждого образца в `reads_summary.qzv` и во входе DADA2 (`dada2_stats.qza`, столбец `input`);
- денойзинг: таблица получена через `denoise-single` с `trim_left` и `trunc_len` из `memory/denoise_choice.md`; длина каждого ASV равна `trunc-len − trim-left`; сумма по каждому образцу в `ASV_table.qza` равна `non-chimeric` в `dada2_stats.qza`; ридов не прибывает по этапам фильтрации; у почвенных образцов после денойзинга не 0 ридов; набор ASV в таблице и в `rep_seq.qza` один;
- классификация: для каждого из трёх методов таксономия есть у каждого ASV ровно один раз, `Confidence` в [0, 1], порог по умолчанию, в provenance записан именно тот классификатор из `data/refs/` (по uuid), который соответствует методу, и классифицированы именно ASV из `rep_seq.qza`;
- `data/refs/VERSIONS.md` содержит имя и верную sha256 каждого классификатора; в `diary.md` есть запись с полем «Итог проверки:».

На промежуточных шагах запускай проверку и убедись, что провалы — только про файлы следующих шагов. Вызови проверку сам перед окончательным ответом. Ответ без пройденной проверки не принимается.

Проверка ловит несогласованность, но не выбирает параметры за человека. Правильность `trim-left` и `trunc-len` — решение человека по графику качества. Числа в `read_counts_R1.tsv` человек сверяет независимо: `gzcat <файл> | wc -l`, делённое на 4, и `seqkit stats`; результат должен совпасть точно. Таксономия сверяется выборочно с выводом `qiime tools export` по 3 ASV на метод.

## 2. Карта проекта, источники и граф

### 2.0. Карта проекта

Где что лежит — в `INDEX.md`. Прочитай его первым и открывай только нужные файлы по ссылкам оттуда.

### Чего агент не может знать сам

- В `data/raw/` у каждого образца два файла, R1 и R2; в анализ идёт только R1 (R2 читается лишь для проверки `reads_R1 == reads_R2`). У образцов LUB в имени файла есть `_first_launch`, а `sample-id` в манифесте без него (`LUB2_S92`); `sample-id` не переименовывать.
- `K_S63` — отрицательный контроль (амплифицированная вода), не почва. Он проходит тот же денойзинг и классификацию, но в сравнения состава почв не входит и нужен для поиска контаминантов. Размер его R1 (1,3 МБ) сопоставим с почвенными, поэтому число ридов само по себе не признак ошибки; о содержимом контроля (сколько ридов, какие ASV) сообщить человеку. `LUB3_S93` — самый маленький R1 (781 КБ): при малом числе ридов или нуле после денойзинга образец не удалять молча, а сообщить.
- Ориентир по порядку результата: у почвенных образцов после денойзинга сохраняется порядка 50–90% ридов; меньше 30% — повод остановиться и сообщить (вероятная причина — неверный `trunc-len`).
- Неизвестно, не угадывать: праймеры V4–V5; на чём обучен классификатор GTDB и откуда взят файл; тип и состав положительного контроля (среди 11 файлов его нет); экологические параметры образцов; номер запуска секвенирования (в метаданных не записан, даты файлов различаются). Всё это `<уточнить>`.
- Для графа неизвестно: что считать хорошим качеством рида (порог Q, минимальное число ридов на образец) — в проекте не задано, решает человек; в отчёте качество описывается числами из сводки, без вывода «годно / негодно». Ожидаемое число ридов в образце не известно: числа в заметки попадают только после расчёта. Нужен ли новый класс онтологии — решает человек. Положительного контроля нет: заметку о нём не создавать.

### 2.2. Онтология в графе

`ontology.yaml` в корне — схема: классы, отношения, атрибуты, правила. Прочитай её первой. Для каждого класса из `ontology.yaml` должна существовать заметка `ontology/<Класс>.md`:

```
---
kind: класс
---
# <Класс>

<определение из ontology.yaml>

Отношения от этого класса: <отношения, у которых класс в domain>.
Атрибуты: <атрибуты, у которых класс в domain, с допустимыми значениями>.

## Связи
- подклассОт: [[<надкласс>]]
```

У всех классов этой онтологии `parent: null`, поэтому раздел «Связи» остаётся пустым. Если заметок классов нет или `ontology.yaml` изменился — создай или обнови их одним скриптом `src/build_ontology_notes.py`, который читает `ontology.yaml` (запуск через `conda run`, как в разделе 3; если PyYAML в окружении нет — спроси человека, пакет не ставь). Определяемые классы из правил (ПочвенныйОбразец, ОтрицательныйКонтроль, ПроверенныйРезультат, ВыполненнаяЗадача) заметок не получают: их выводит скрипт проверки.

### 2.3. Заметки об объектах

Каждый объект работы — заметка `notes/<название>.md`:

```
---
type: Образец
role: отрицательный контроль
---
# Образец K_S63

Отрицательный контроль (амплифицированная вода). Ридов R1: <число из results/read_counts_R1.tsv>.

## Связи
- тип: [[Образец]]
- входитВ: [[Сырые риды R1 проекта]]
- хранитсяВ: [[data/raw/K_S63_R1_001.fastq.gz]]
```

Правила:
- Название называет экземпляр: «Образец Kr1_S80», «Таблица числа ридов по образцам». Название класса само по себе названием заметки не бывает.
- В названии нет символов `/ \ : # | [ ]`: пиши «число ридов на образец», а не «ридов/образец». Символ `/` создаёт вложенную папку, и ссылки ломаются.
- Строка `- тип: [[<Класс>]]` обязательна: она связывает объект с классом в графе. У образца первым в начале заметки стоит поле `role:` (`почва` или `отрицательный контроль`); у задачи — `status:`.
- Остальные связи — только отношения из `ontology.yaml`, от области определения к области значений. Связь записывается в заметке, от которой она идёт.
- Файлы проекта — `data/`, `src/`, `results/`, `work/`, `reports/` — отдельные заметки не получают: на них ссылаются по пути от корня, например `[[data/raw/Kr1_S80_R1_001.fastq.gz]]`, `[[src/count_reads.py]]`, `[[results/read_counts_R1.tsv]]`, `[[work/qzv/reads_summary.qzv]]`. Файл образца LUB называется с `_first_launch`, а заметка — по `sample-id`: «Образец LUB2_S92» → `[[data/raw/LUB2_S92_first_launch_R1_001.fastq.gz]]`. В графе у образца только файл R1; R2 упоминается в тексте заметки.
- Числа в заметках — из вывода команды или файла в `results/`, с единицами («ридов», «нуклеотидов»).
- Отчёт пишется, только если человек просил отчёт. Отчёт — сам файл `reports/<название>.md`: в начале `type: Отчёт`, в конце раздел «Связи», как у заметок объектов. Литературные источники для этих задач не нужны; ссылок на `paper/` без DOI, проверенного человеком, не ставить (запрет 5).
- Объект, для которого в онтологии нет класса, — новый тип и строка «Новый тип: <почему>». `ontology.yaml` не меняй: решение о новом классе принимает человек.
- Заметку создавай в момент, когда объект появился в работе: набор данных — при чтении, метод — при выборе, результат — после расчёта, проверку — после проверки.
- Заметка, которая закрывает подзадачу, ссылается на неё: эксперимент и проверка — `решает`, отчёт — `выполняет`.

Объекты малой цели:

| Класс | Заметки (названия) | Файлы, на которые ведёт `хранитсяВ` |
|---|---|---|
| Образец | «Образец <sample-id>» × 11: десять с `role: почва`, «Образец K_S63» с `role: отрицательный контроль` | `data/raw/<…>_R1_001.fastq.gz` |
| НаборДанных | «Сырые риды R1 проекта» (11 образцов входят в него); «Импортированные риды R1» | `data/raw/`; `work/qza/raw_reads_single.qza` |
| Метод | «Подсчёт ридов скриптом count_reads»; «Сводка качества demux summarize» | `src/count_reads.py`; метод QIIME 2 без файла — связь не нужна |
| Эксперимент | «Подсчёт ридов по 11 образцам»; «Построение сводки качества»; «Сравнение числа ридов с медианой почв» | — |
| Результат | «Таблица числа ридов по образцам»; «Сводка качества ридов»; «Сравнение контроля с почвами» | `results/read_counts_R1.tsv`; `work/qzv/reads_summary.qzv`; `results/reads_vs_median.tsv` |

### 2.4. Задачи

Сообщение человека, которое требует работы с файлами проекта, — новая задача верхнего уровня, даже если она продолжает прежнюю. Вопрос, на который достаточно ответить словами, задачей не становится.

Заметка задачи — `tasks/<название>.md`, название — действие. Названия заметок во всём проекте различны: задача «Подсчитать риды…», эксперимент «Подсчёт ридов…».

```
---
type: Задача

---
# <название>

Запрос пользователя: «<его слова дословно>»   (только у задачи верхнего уровня)

Готово, когда: <проверяемое условие: файл, число, команда и её результат>
Не входит: <что делать не нужно>

## Связи
- тип: [[Задача]]
- подзадачаОт: [[<родительская задача>]]   (только у подзадачи)
```

Подзадачи:
- Если необходимо, раздели задачу на 2–5 подзадач: каждая заканчивается объектом, который её закрывает (эксперимент, проверка или отчёт). Порядок выполнения — раздел «План» в заметке родительской задачи: названия подзадач по строке, без ссылок.
- Запиши задачу и все подзадачи со статусом «открыта» до любых расчётов и покажи план человеку: по строке на подзадачу. Чисел, которых ещё нет, в заметках задач не пиши.

Задачи малой цели:

**Задача 1 — «Подсчитать риды и оценить их качество».**
- Запрос пользователя: «Посчитай, сколько ридов в каждом образце, и оцени качество ридов».
- Готово, когда: (а) `results/read_counts_R1.tsv` содержит 11 строк со столбцами из раздела 0 и `reads_R1 == reads_R2` у каждого образца; (б) для каждого образца число ридов R1 равно `gzcat <файл R1> | wc -l`, делённому на 4 (`zcat` вне macOS), расхождение 0 — команда и результат записаны в «Итог»; (в) `qiime tools validate work/qzv/reads_summary.qzv` сообщает success, а числа ридов по образцам в сводке равны таблице из (а).
- Не входит: выбор `trim-left` и `trunc-len`, денойзинг, классификация; перезапись существующих `results/` и `work/` без подтверждения (если файл есть — проверь его, а не пересоздавай).
- План: 1) Подсчитать риды по образцам (закрывает эксперимент «Подсчёт ридов по 11 образцам»); 2) Сверить числа ридов независимой командой (закрывает проверка «Сверка числа ридов с gzcat»); 3) Проверить сводку качества (закрывают эксперимент «Построение сводки качества» и проверка «Валидация сводки качества»).

**Задача 2 — «Составить отчёт о числе и качестве ридов».** Опирается на задачу 1: начинается, когда задача 1 «выполнена» или «принята»; если она «заблокирована» — задача 2 тоже «заблокирована».
- Запрос пользователя: «Составь отчёт по ридам: сравни отрицательный контроль с почвенными образцами и опиши качество ридов».
- Готово, когда: (а) `reports/<название>.md` существует, в начале `type: Отчёт`, есть таблица по 11 образцам и разделы «Число ридов», «Контроль и почвенные образцы», «Качество ридов», «Связи»; (б) в разделе о контроле указаны число ридов `K_S63`, медиана по десяти почвенным образцам и положение `LUB3_S93` (самый маленький R1) относительно медианы; (в) каждое число отчёта совпадает с файлами `results/` и экспортом сводки качества: скрипт `src/check_report_numbers.py` возвращает 0; (г) отчёт связан `основанНа` с результатами и `выполняет` с задачей.
- Не входит: таксономия, сравнение классификаторов, литература, выбор `trim-left` и `trunc-len`, вывод «годно / негодно» о качестве.
- План: 1) Сравнить число ридов контроля с почвенными образцами (закрывает эксперимент «Сравнение числа ридов с медианой почв», результат `results/reads_vs_median.tsv`, скрипт в `src/`); 2) Написать отчёт о ридах (закрывает отчёт; качество — из `qiime tools export` сводки в `work/qzv_export/`); 3) Сверить числа отчёта с таблицами (закрывает проверка «Сверка чисел отчёта с таблицами»).

Статусы (поле `status`):

| статус | кто ставит | когда |
|---|---|---|
| открыта | агент | задача записана |
| в работе | агент | начал выполнять |
| выполнена | агент | условие «Готово, когда» проверено командой; раздел «Итог» записан |
| заблокирована | агент | условие недостижимо или нужна остановка из раздела 5 (например, выбор `trim-left`): причина и вопрос человеку в разделе «Итог» |
| принята | агент | существует подтверждение выполнения: слова человека |

- Статус меняется в момент события, по одной подзадаче: «в работе» — до первой команды подзадачи; «выполнена» и итог — сразу после проверки её условия, до начала следующей. По статусам в Obsidian человек видит ход работы.
- При статусе «выполнена» — раздел `## Итог` перед «Связями»: что сделано, какие файлы и заметки появились, чем проверено (команда и результат), 2–5 строк. Итог выводи и человеку в сессии.
- Родительская задача выполнена, когда выполнены все её подзадачи; её итог — сводка по подзадачам.
- «Принята» ставится только после слов человека «принимаю» (или равных по смыслу) и распространяется на подзадачи. В итог допиши строку «Принято пользователем: «<его слова>»». Просьба переделать возвращает задачу в статус «в работе».
- Принятая задача закрыта: новые заметки не ссылаются на неё связями `решает` и `выполняет`. Новая работа — новая задача; связь с прежней работой идёт через объекты (отчёт `основанНа` результате).

## 5. Протокол работы

Режим работы: конвейер.

Шаги идут строго по порядку; каждый записывается в `diary.md` и завершается проверкой своего результата:
1. Подсчёт ридов и проверка манифеста → `results/read_counts_R1.tsv`. Проверка: сверка человеком (раздел 1).
2. Импорт (`SingleEndFastqManifestPhred33V2`) → `work/qza/raw_reads_single.qza`; `qiime demux summarize` → `work/qzv/reads_summary.qzv`. Проверка: `qiime tools validate`; число ридов в сводке равно `read_counts_R1.tsv`. **Остановка:** человек выбирает `trim-left` и `trunc-len` и записывает в `memory/denoise_choice.md` с обоснованием.
3. `dada2 denoise-single` один раз для всех 11 образцов с параметрами из `denoise_choice.md`, остальные — как в пайплайне пользователя (`--p-max-ee 3`, `--p-min-fold-parent-over-abundance 2`) → `ASV_table.qza`, `rep_seq.qza`, `dada2_stats.qza`, `dada2_stats.qzv`. Проверка: `checks/check.py` не выдаёт провалов по разделам импорта и денойзинга; доли сохранённых ридов по образцам записаны в дневник.
4. Проверка готовых классификаторов (не переобучать). Проверка: источники, даты и sha256 трёх файлов записаны в `data/refs/VERSIONS.md`; каждый файл загружается текущим QIIME 2 — `classify-sklearn` на 5 ASV из шага 3 завершается без ошибки.
5. Классификация тремя методами по одному, `--p-n-jobs` 1–2 (классификаторы по 180–220 МБ занимают несколько ГБ памяти) → `work/qza/taxonomy_<метод>.qza`. Проверка: `checks/check.py` (команда из раздела 1) возвращает 0.

После шага 5 — остановка и отчёт человеку. Сравнение методов не начинать.

Код — в `src/`, запускается до того, как результат сообщается. Каждый вывод сопровождается способом проверки. Если проверка шага не прошла — найти причину, исправить, повторить; один коммит на шаг после успешной проверки.
