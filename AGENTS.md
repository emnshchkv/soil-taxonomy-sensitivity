# AGENTS.md — Чувствительность таксономического профиля бактериальных сообществ городских почв Москвы к выбору классификатора и референсной базы данных

## 0. Цель и образ результата

Методологический вопрос проекта: насколько таксономический состав бактериальных сообществ почв Москвы (16S рРНК, V4–V5, QIIME 2 2025.7) и выводы о нём зависят от классификатора и референсной базы при фиксированной обработке ридов.

**Текущий этап: всё до сравнения классификаторов** — подсчёт ридов, импорт и сводка качества, денойзинг, классификация. Сравнение методов (таблица соответствий номенклатур, доля неклассифицированных, согласованность, отчёт) на этом этапе не делается и не начинается.

Методы этапа — три запуска `classify-sklearn` с готовыми классификаторами и пороги по умолчанию (`confidence 0.7`): `sklearn_silva138`, `sklearn_gtdb`, `sklearn_gg2`. Методы `classify-consensus-vsearch` и `classify-consensus-blast` отложены: им нужны референсные FASTA и таксономия SILVA, которых в `data/refs/` нет.

В конце этапа в проекте существуют:
- `results/read_counts_R1.tsv` — число и длина ридов по 11 образцам: `sample-id`, `reads_R1`, `reads_R2`, `mean_len_R1`, `min_len_R1`, `max_len_R1`;
- `work/qza/raw_reads_single.qza` и `work/qzv/reads_summary.qzv` — импорт и сводка качества;
- `memory/denoise_choice.md` — решение человека, строки `trim-left: <число>` и `trunc-len: <число>` и обоснование;
- `work/qza/ASV_table.qza`, `work/qza/rep_seq.qza`, `work/qza/dada2_stats.qza`, `work/qzv/dada2_stats.qzv` — результат денойзинга;
- `work/qza/taxonomy_sklearn_silva138.qza`, `work/qza/taxonomy_sklearn_gtdb.qza`, `work/qza/taxonomy_sklearn_gg2.qza` — таксономия трёх методов;
- `data/refs/VERSIONS.md` — источник, дата и sha256 каждого из трёх классификаторов;
- `diary.md` — журнал.

Ничего больше создавать не надо.

## 1. Критерий готовности

Этап считается выполненным, когда проходит проверка (из корня проекта, в окружении `qiime2-amplicon-2025.7`):

```
conda run --no-capture-output -n qiime2-amplicon-2025.7 python3 checks/check.py
```

Проверка возвращает 0 при успехе и 1 при любом провале, провалы печатает списком. Она проверяет:
- метаданные и манифест: 11 образцов (`K_S63` — `negative_control`, остальные `soil`), в манифесте только R1, все файлы существуют; контрольные суммы `data/raw/` совпадают с `data/raw.sha256`; `data/raw/` и `checks/` закрыты от записи;
- число ридов: `reads_R1 == reads_R2`, и то же число у каждого образца в `reads_summary.qzv` и во входе DADA2 (`dada2_stats.qza`, столбец `input`);
- денойзинг: таблица получена через `denoise-single` с `trim_left` и `trunc_len` из `memory/denoise_choice.md`; длина каждого ASV равна `trunc-len − trim-left`; сумма по каждому образцу в `ASV_table.qza` равна `non-chimeric` в `dada2_stats.qza`; ридов не прибывает по этапам фильтрации; у почвенных образцов после денойзинга не 0 ридов; набор ASV в таблице и в `rep_seq.qza` один;
- классификация: для каждого из трёх методов таксономия есть у каждого ASV ровно один раз, `Confidence` в [0, 1], порог по умолчанию, в provenance записан именно тот классификатор из `data/refs/` (по uuid), который соответствует методу, и классифицированы именно ASV из `rep_seq.qza`;
- `data/refs/VERSIONS.md` содержит имя и верную sha256 каждого классификатора; в `diary.md` есть запись с полем «Итог проверки:».

На промежуточных шагах запускай проверку и убедись, что провалы — только про файлы следующих шагов. Вызови проверку сам перед окончательным ответом. Ответ без пройденной проверки не принимается.

Проверка ловит несогласованность, но не выбирает параметры за человека. Правильность `trim-left` и `trunc-len` — решение человека по графику качества. Числа в `read_counts_R1.tsv` человек сверяет независимо: `gzcat <файл> | wc -l`, делённое на 4, и `seqkit stats`; результат должен совпасть точно. Таксономия сверяется выборочно с выводом `qiime tools export` по 3 ASV на метод.

## 2. Карта проекта и источники

Где что лежит — в `INDEX.md`. Прочитай его первым и открывай только нужные файлы по ссылкам оттуда.

### Чего агент не может знать сам

- В `data/raw/` у каждого образца два файла, R1 и R2; в анализ идёт только R1 (R2 читается лишь для проверки `reads_R1 == reads_R2`). У образцов LUB в имени файла есть `_first_launch`, а `sample-id` в манифесте без него (`LUB2_S92`); `sample-id` не переименовывать.
- `K_S63` — отрицательный контроль (амплифицированная вода), не почва. Он проходит тот же денойзинг и классификацию, но в сравнения состава почв не входит и нужен для поиска контаминантов. Размер его R1 (1,3 МБ) сопоставим с почвенными, поэтому число ридов само по себе не признак ошибки; о содержимом контроля (сколько ридов, какие ASV) сообщить человеку. `LUB3_S93` — самый маленький R1 (781 КБ): при малом числе ридов или нуле после денойзинга образец не удалять молча, а сообщить.
- Ориентир по порядку результата: у почвенных образцов после денойзинга сохраняется порядка 50–90% ридов; меньше 30% — повод остановиться и сообщить (вероятная причина — неверный `trunc-len`).
- Неизвестно, не угадывать: праймеры V4–V5; на чём обучен классификатор GTDB и откуда взят файл; тип и состав положительного контроля (среди 11 файлов его нет); экологические параметры образцов; номер запуска секвенирования (в метаданных не записан, даты файлов различаются). Всё это `<уточнить>`.

## 4. Запреты

1. Не изменять, не удалять и не перезаписывать `data/raw/`. `[среда]` — права только на чтение (`chmod -R a-w data/raw`), контрольные суммы в `data/raw.sha256` проверяет `checks/check.py`.
2. Не удалять и не перезаписывать существующие файлы в `data/meta/` и `data/refs/`; новые создавать можно. `[вызов]` — правило подтверждения для записи в эти пути в настройках агента; `data/meta/` дополнительно под `git`, откат — `git checkout`.
3. Не читать и не выводить содержимое `.env` и других файлов с ключами. `[вызов]` — запрет чтения этих путей в настройках агента; ключи хранить вне папки проекта.
4. Не выполнять `git push`, `rm -rf`, `sudo` без подтверждения. `[вызов]` — правило подтверждения для этих команд в настройках агента.
5. Не выдумывать числа и ссылки: каждое число в отчёте — из вывода команды или файла в `results/`, каждая ссылка на литературу — с DOI, который проверяет человек. `[окно]` — обеспечивается только словом; поэтому проверка человеком обязательна.
6. Не изменять, не удалять и не создавать файлы в `checks/`. `[среда]` — права только на чтение (`chmod -R a-w checks`; чтобы поправить проверку самому: `chmod -R u+w checks`); `checks/check.py` сам падает, если `checks/` открыта для записи.

## 5. Протокол работы

Режим работы: конвейер.

Шаги идут строго по порядку; каждый записывается в `diary.md` и завершается проверкой своего результата:
1. Подсчёт ридов и проверка манифеста → `results/read_counts_R1.tsv`. Проверка: сверка человеком (раздел 1).
2. Импорт (`SingleEndFastqManifestPhred33V2`) → `work/qza/raw_reads_single.qza`; `qiime demux summarize` → `work/qzv/reads_summary.qzv`. Проверка: `qiime tools validate`; число ридов в сводке равно `read_counts_R1.tsv`. **Остановка:** человек выбирает `trim-left` и `trunc-len` и записывает в `memory/denoise_choice.md` с обоснованием.
3. `dada2 denoise-single` один раз для всех 11 образцов с параметрами из `denoise_choice.md`, остальные — как в пайплайне пользователя (`--p-max-ee 3`, `--p-min-fold-parent-over-abundance 2`) → `ASV_table.qza`, `rep_seq.qza`, `dada2_stats.qza`, `dada2_stats.qzv`. Проверка: `checks/check.py` не выдаёт провалов по разделам импорта и денойзинга; доли сохранённых ридов по образцам записаны в дневник.
4. Проверка готовых классификаторов (не переобучать). Проверка: источники, даты и sha256 трёх файлов записаны в `data/refs/VERSIONS.md`; каждый файл загружается текущим QIIME 2 — `classify-sklearn` на 5 ASV из шага 3 завершается без ошибки.
5. Классификация тремя методами по одному, `--p-n-jobs` 1–2 (классификаторы по 180–220 МБ занимают несколько ГБ памяти) → `work/qza/taxonomy_<метод>.qza`. Проверка: `checks/check.py` (команда из раздела 1) возвращает 0.

После шага 5 — остановка и отчёт человеку. Сравнение методов не начинать.

Код — в `src/`, запускается до того, как результат сообщается. Каждый вывод сопровождается способом проверки. Если проверка шага не прошла — найти причину, исправить, повторить; один коммит на шаг после успешной проверки.
